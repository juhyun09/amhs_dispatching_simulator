# AMHS Dispatching Simulator

반도체 팹의 OHT(Overhead Hoist Transport) 기반 웨이퍼 반송 시스템(AMHS)을
이산 사건 시뮬레이션으로 재현하고, 결정론적 디스패칭 알고리즘과 AI 에이전트를
하이브리드로 결합해 운영 의사결정을 지원하는 프로젝트입니다.

## 왜 이 프로젝트인가

AMHS는 반도체 팹 운영에서 핵심적인 인프라입니다. 다수의 OHT 차량이 스토커와
공정 장비(툴 포트) 사이를 오가며 FOUP(웨이퍼 카세트)을 실어 나르는데, 이 반송을
어떻게 스케줄링하느냐에 따라 팹 전체의 처리량과 장비 가동률이 크게 달라집니다.

이 프로젝트는 실제 하드웨어 없이도 AMHS의 핵심 문제 — **제한된 차량 자원으로
다수의 반송 요청을 어떤 순서로 처리할 것인가** — 를 소프트웨어로 재현하고,
여러 디스패칭 전략의 성능을 실험적으로 비교하는 것을 목표로 합니다.

## 핵심 아이디어

일반적인 반송 시뮬레이터에 그치지 않고, **"AI를 어디에 쓰고 어디엔 안 쓸지"를
설계의 중심에 둡니다.**

- 초당 수십~수백 건 발생하는 **일상적인 디스패칭 결정**은 그대로 결정론적
  알고리즘(nearest-idle-vehicle, zone-based 등)이 처리합니다. 빠르고 예측
  가능해야 하는 영역이기 때문입니다.
- **hot lot 우선순위 충돌, 데드락 등 예외적이고 모호한 상황**에서만 Claude
  에이전트가 개입해, 상황을 진단하고 조치를 제안합니다. 제안은 즉시 실행되지
  않고 별도 승인 단계를 거치도록 설계했습니다(least-privilege 원칙 적용).
- 운영자는 자연어로 "차량을 2대 늘리면 처리량이 얼마나 좋아지나요?" 같은
  what-if 질문을 던질 수 있고, 에이전트가 시뮬레이션을 재실행해 답변합니다.

즉 AI는 장식이 아니라, **지연시간·비용·설명가능성을 고려해 개입 지점을
의도적으로 제한한 설계 요소**로 들어갑니다.

## 프로젝트 목표

- [ ] 20~30개 노드 규모의 레일 네트워크와 5~10대의 OHT 차량으로 구성된
      AMHS를 이산 사건 시뮬레이션으로 구현한다
- [ ] 서로 다른 디스패칭 알고리즘(nearest-idle-vehicle vs zone-based)의
      평균 반송 시간, 차량 가동률, 처리량을 정량적으로 비교한다
- [ ] MCP 서버를 통해 시뮬레이터 상태/지표를 도구로 노출하고, Claude
      에이전트가 이를 활용해 자연어 질의응답과 예외 상황 개입을 수행하게 한다
- [ ] 에이전트의 개입이 실제로 도움이 되는지(정시 배송률, 데드락 해소 시간 등)
      평가셋 기반으로 검증한다

## 아키텍처

```
┌─────────────────────────┐
│   시뮬레이터 코어         │
│  ┌────────┐ ┌─────────┐ │
│  │  Rail   │ │  Job    │ │
│  │ Network │ │Generator│ │
│  └────────┘ └─────────┘ │
│  ┌────────┐ ┌─────────┐ │
│  │ Vehicle │ │Dispatcher│ │
│  │  (FSM)  │ │ (v1/v2) │ │
│  └────────┘ └─────────┘ │
│        └── Metrics ──┘   │
└───────────┬──────────────┘
            │ 상태 / 지표
            ▼
┌─────────────────────────┐
│        MCP 서버          │
│ get_snapshot()            │
│ get_metrics(window)       │
│ run_whatif(params)        │
│ propose_reroute(id, 사유) │  ← 제안만, 실행은 별도 승인
└───────────┬──────────────┘
            ▼
┌─────────────────────────┐
│      Claude 에이전트      │
│ · 자연어 운영 콘솔          │
│ · 예외 상황(hot lot 충돌,   │
│   데드락)에서만 개입         │
└─────────────────────────┘
```

## 사용 기술

| 영역 | 기술 | 비고 |
|---|---|---|
| 시뮬레이션 엔진 | Python, `simpy` | 이산 사건 시뮬레이션 |
| 그래프/라우팅 | BFS / Dijkstra | 레일 네트워크 최단경로 |
| AI 통합 | Claude API, MCP | 자연어 질의응답, 예외 상황 개입 |
| 시각화 | Streamlit, Plotly | 지표 대시보드, 리플레이 |
| 언어 | Python | — |

## 주요 기능

**MVP**
- 레일 네트워크 그래프 기반 시뮬레이션
- Job 생성(포아송 프로세스) 및 차량 상태머신
- Dispatcher v1 (nearest-idle-vehicle)
- 기본 지표 수집(평균 반송 시간, 가동률, 처리량)

**확장 기능**
- MCP 서버를 통한 자연어 what-if 시뮬레이션
- 예외 상황 하이브리드 에이전트 개입(제안-승인 구조)
- Dispatcher v2(zone-based)와의 A/B 비교
- Streamlit 대시보드 및 리플레이 시각화

## 한계와 향후 개선점

- 현재는 단일 레이어 레일 네트워크만 다루며, 실제 팹의 멀티루프/멀티레이어
  OHT 구조는 반영하지 않았습니다.
- 단일 트랙 구간에서의 충돌·데드락 방지(segment locking)는 스트레치
  목표로, 시간 제약에 따라 구현 범위가 달라질 수 있습니다.
- 에이전트 개입의 효과는 소규모 평가셋(5~10개 시나리오) 기반으로만
  검증되어, 더 큰 규모의 검증이 필요합니다.
